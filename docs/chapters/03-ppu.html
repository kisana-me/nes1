PPU(グラフィック)実装

この章のゴール

NES の映像チップ PPU (Picture Processing Unit) を実装し、 エミュレータに「目に見える画面」を与えます。エミュレータ開発の中で最も複雑な部分です。 この章が終わると、ROM が指定した背景とスプライトが Canvas に表示されます。

実装したファイル:

  • src/ppu.ts — PPU 本体(レジスタ、VRAM、スキャンライン描画)
  • src/nes.ts — CPU と PPU を同期して動かす本体クラス
  • src/main.ts — ROM 読み込みと Canvas 描画ループ

PPU の考え方 — 「ビットマップ」ではなく「タイル」

現代の画面は「全ピクセルの色の配列(フレームバッファ)」ですが、 256×240×1 バイトでも約 60KB —— NES の VRAM(2KB)には全く入りません。 そこで NES は画面を 8×8 ピクセルのタイルの敷き詰めとして表現します。 

パターンテーブル (CHR-ROM)     ネームテーブル (VRAM)        画面
「タイルの絵の辞書」            「どこにどのタイルを置くか」
┌────┬────┐                ┌──┬──┬──┬──┐
│ 🌱 │ 🧱 │  タイル0,1,...   │ 1│ 1│ 1│ 1│ ← 32x30 個の    🧱🧱🧱🧱
│ ⛅ │ 🚪 │  256 個 x 2 面   │ 0│ 2│ 0│ 0│    タイル番号  → 🌱⛅🌱🌱
└────┴────┘                └──┴──┴──┴──┘
  • パターンテーブル ($0000-$1FFF, カセットの CHR-ROM) — タイルの絵。8×8 ピクセル × 2bit = 16 バイト/枚
  • ネームテーブル ($2000-$2FFF, VRAM) — 32×30 = 960 個のタイル番号で 1 画面
  • 属性テーブル — ネームテーブル末尾 64 バイト。16×16 ピクセルのブロックごとにパレット(色セット)を指定
  • パレット RAM ($3F00-) — 64 色のマスターパレットから使う色を選ぶ

タイル 1 枚 = 2 ビットプレーン

タイルの各ピクセルは 0〜3 の 2 ビット。これを「ビットプレーン」2 枚に分けて格納します。 

plane0 (下位bit)   plane1 (上位bit)   合成結果 (ピクセル値 0-3)
0 1 1 0 ...        0 0 1 1 ...        0 1 3 2 ...

const lo = chr[tile*16 + y];      // plane0
const hi = chr[tile*16 + y + 8];  // plane1
color = ((hi >> bit) & 1) << 1 | ((lo >> bit) & 1);

値 0 は「透明」。パレット値 0 のピクセルには背景色($3F00)が表示されます。

スプライト — 動くもの担当

背景タイルとは別に、PPU は最大 64 枚のスプライト(自由な位置に置ける 8×8/8×16 タイル)を持ちます。 スプライトの情報は OAM という専用メモリに 4 バイト/枚で入っています:

バイト内容
0Y 座標(表示位置 - 1)
1タイル番号
2属性: パレット、左右/上下反転、背景との前後関係
3X 座標

毎フレーム、ゲームは $4014 に書き込むだけで RAM の 256 バイトを OAM へ一括転送できます (OAM DMA)。この間 CPU は 513 サイクル停止します —— nes.ts では cpu.stall に加算して再現しています。

実機の制約もそのまま実装しています:

  • 1 スキャンラインに表示できるスプライトは 8 枚まで(9 枚目からは消える。昔のゲームのチラつきの原因)
  • スプライト 0 ヒット: スプライト 0 番と背景の不透明ピクセルが重なると ステータスレジスタにフラグが立つ。ゲームはこれで「画面の分割位置」を検出する

CPU から PPU をどう操作するか

PPU は CPU バスの $2000-$2007 に 8 個のレジスタとして見えています。

アドレス名前役割
$2000PPUCTRLNMI 有効化、スプライトサイズ、パターンテーブル選択など
$2001PPUMASK背景/スプライトの表示 ON/OFF
$2002PPUSTATUSVBlank・スプライト0ヒットの状態(読むと VBlank フラグはクリア)
$2003/4OAMADDR/DATAOAM への直接アクセス
$2005PPUSCROLLスクロール位置(X→Y の順に 2 回書く)
$2006PPUADDRVRAM アドレス(上位→下位の順に 2 回書く)
$2007PPUDATAVRAM の読み書き(アドレスは自動インクリメント)
$2007 の読み出しは 1 テンポ遅れるのが実機の仕様です。読み出した値は内部バッファに入り、 返ってくるのは「前回読んだ値」。正しい値が欲しければ 2 回読む必要があります (パレット領域だけは即時)。テスト testPpuDataBuffer でこの挙動を検証しています。

スクロールの心臓部 — loopy レジスタ

PPU 内部には v(現在の VRAM アドレス)と t(スクロール設定のテンポラリ)という 2 つの 15 ビットレジスタがあります。ビット配置が絶妙で、スクロール座標と VRAM アドレスが同じレジスタで表現されます: 

 yyy NN YYYYY XXXXX
 │   │  │     └─ coarse X: タイル単位の X 位置 (0-31)
 │   │  └─────── coarse Y: タイル単位の Y 位置 (0-29)
 │   └────────── ネームテーブル選択 (4 画面のどれか)
 └────────────── fine Y: タイル内の Y (0-7)

描画中、v は次のように動きます(エミュレータでも同じ順序を再現):

  1. タイルを 1 枚描くたび coarse X++(31 を超えたら隣のネームテーブルへ)
  2. ライン末尾 (dot 256) で fine Y++
  3. dot 257 で「水平成分だけ」t から v へコピー(次のラインは左端から)
  4. プリレンダーラインの dot 280 で「垂直成分」を t から v へコピー(次のフレームは先頭から)

この仕組みのおかげで、ゲームはフレーム途中でスクロール値を書き換えて画面を分割できます (ステータスバーは固定、下だけスクロール、など)。ライン単位で v を参照して描画する本実装でも、 この分割テクニックはそのまま動きます。

タイミング — CPU と PPU の同期

PPU は CPU の 3 倍のクロックで動き、1 フレーム = 262 スキャンライン × 341 ドットです。 nes.ts の中心はこのループ: 

step(): number {
  const cpuCycles = this.cpu.step();       // CPU を 1 命令
  for (let i = 0; i < cpuCycles * 3; i++) {
    this.ppu.tick();                       // その 3 倍 PPU を進める
  }
  return cpuCycles;
}

1 フレームの流れ:

ライン 0-239   : 可視領域。ライン単位でフレームバッファに描画
ライン 240     : 何もしない
ライン 241 dot1: VBlank フラグ ON → (有効なら) CPU へ NMI!
ライン 242-260 : VBlank 継続。ゲームはこの間に VRAM を更新する
ライン 261     : プリレンダー。フラグを全クリアして次フレームの準備

描画は「ドット単位」ではなく「ライン単位」でまとめて行うスキャンライン方式を採用しました。 精度と速度のバランスが良く、大半のゲームはこれで正しく動きます。

Canvas への転送

PPU が作るのは「パレット番号の並び」です。これを RGBA に変換して Uint32Array のフレームバッファへ書き、毎フレーム putImageData 一発で Canvas に転送します。 

const imageData = ctx.createImageData(256, 240);
const imagePixels = new Uint32Array(imageData.data.buffer); // 同じメモリを 32bit で見る

imagePixels.set(nes.frameBuffer);  // コピー 1 回
ctx.putImageData(imageData, 0, 0);

1 ピクセルずつ fillRect する方法に比べて桁違いに高速です。 CSS 側で image-rendering: pixelated を指定し、拡大してもドットがぼやけないようにしています。

この章の動作確認手順

  1. npm test — CPU テストに加え、PPU テスト 9 件が pass すること。 特に testBackgroundRendering は「機械語プログラムがパレットとネームテーブルを設定 → 実際に 5 フレーム実行 → フレームバッファの色を検証」というエンドツーエンドテストです
  2. npm run serve でブラウザを開き、手持ちの自作/フリー .nes ファイル(NROM)を読み込むと画面が表示されます (テスト用のオリジナルゲーム ROM は次章で作ります!)
